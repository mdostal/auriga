## [0.2.0] - 2026-09-04

**Auriga now talks to Pantheon instead of Multica directly — the architecture violation the pantheon-v2-l2 adapter was always meant to close — plus multi-tenant config support and a string of real bugs found and fixed while dogfooding both against live deployments.**

### Added

- **`pantheon-v2-l2` real implementation, cutover from direct Multica integration** (PR #65): the adapter's two factories are no longer stubs — both now call Pantheon's own `core-api` backlog API over HTTP (`http-runner.mjs` + `curl`, keeping the required synchronous contract), which itself wraps Multica's REST API server-side. Auriga's container now holds zero Multica credentials, runs no Multica CLI, and has no direct network path to Multica — only to `core-api`. This also fixes the concrete reason Auriga's router could never drain the board from inside its own container: the `multica` CLI binary is a native macOS binary that can't execute in a Linux container at all; `curl` is a standard package. GitHub-based PR discovery was re-ported back into the new adapter (PR #69) after Multica's native issue↔PR linkage turned out to be empty on the live workspace (no GitHub App configured) — every `in_review` issue was sitting un-reviewed regardless of how many real PRs existed until this landed.
- **Multi-tenant config externalization** (PR #73, pant-70): a new `AURIGA_CONFIG` env var points at a partial JSON override file — any top-level key overrides `config.mjs`'s corresponding export, absent keys keep hardcoded defaults; fails closed (exits non-zero) on an unreadable/malformed file rather than silently falling back to the full project list. `AURIGA_INSTANCE_ID`/`AURIGA_TENANT_ID` stamp every JSONL log line so multiple concurrent router instances are separable in logs — the foundation for running Auriga per-tenant rather than one shared instance.
- **Per-god project registry entries** (PR #72, pant-59): six new per-god Multica projects registered so the router's dispatch loop scans and routes tickets filed against them; the Consus god-project routes decision seeds to `minerva-dev` via the existing `isSeed()` check, everything else routes to its aligned build lane.

### Fixed

- **`PANT-4`-style done↔in_review thrash** (this release, GitHub issue #76): `detectFalseDone`'s fallback path demoted a `done` issue on ANY open PR that identity-matched the story, without checking for a co-existing MERGED identity-matching PR — so a real merge and an unrelated stray open PR in the same repo could fight forever. Fixed with a merged-PR guard; a real merge always wins.
- **Unbounded zombie-recovery retries** (this release, GitHub issue #75): `detectZombies` re-fired `assign`/`rerun` on a stuck issue every cycle indefinitely (one real stall ran 3+ hours with no recovery). Now bounded via the issue's own run count (`cfg.CAPS.zombieMaxAttempts`, default 3) — past the cap it gives up cleanly (logs + comments on the issue) instead of looping. Deliberate stopgap pending Hellsing, which would own real actuation but has no runnable code today.
- **Epic status rollup didn't recognize `shipped`/`complete` as terminal** (this release): the dashboard's `deriveEpicStatus` only treated story status `done` as finished, so every epic reconciled to `shipped` during the v0.1.0 release rolled up to `in-progress` on the dashboard instead of `done`. Found by the release verification suite itself (`npm run test:all`, which `npm test` alone doesn't cover).
- **Bodyless POST requests rejected by Pantheon's API** (PR #67): `rerunIssue()`'s bodyless POST was sending a `content-type` header with no body, which Fastify's strict parser rejects (`FST_ERR_CTP_EMPTY_JSON_BODY`) — directly blocked live verification of the pantheon-v2-l2 cutover.
- **Supervisor single-instance guard used a PID file, not a real lock** (PR #68): a stale `/tmp/auriga-supervisor.pid` survives a plain `docker restart` (writable layer persists, only the PID namespace resets), so a leftover PID could coincidentally collide with the new boot's own PID 1 and wedge the container in a permanent crash loop. Switched to `flock -n 9` on a lock file, tied to a live file descriptor the kernel releases the instant the holder dies.
- **Board-wide PR scan had no per-call timeout** (PR #70): `listCandidatePullRequests()` does up to ~100+ sequential `gh pr list` calls with no timeout; one slow/hanging repo could stall the whole scan indefinitely, starving the review lane's PR cache for every issue that cycle. Bounded to 15s per call.
- **Stale-workspace project registry entries** (PR #71): 4 of 5 entries in `projects.json` pointed at a Multica workspace this host no longer talks to — silently never matched a real issue rather than causing visible harm, but implied live per-repo routing that structurally couldn't happen. Pruned to the one real, live project (plus Minerva's documented dispatch-ineligible placeholder).
- **Stale "Pantheon Core" project registration** (PR #66): the existing registry entry pointed at a different, stale Multica workspace than the one this install's `core-api` is actually configured against — filing a ticket there returned `project not found in this workspace`. Registered the real project in the correct workspace.
- **`isSeed()` misclassified standalone bug/fix tickets as unplanned seeds** (PR #74): a childless, top-level, already-scoped ticket (no parent, no children) is indistinguishable from a genuine idea by that heuristic alone — Minerva correctly declined it and unassigned, but the next cycle re-evaluated `isSeed()` on the unchanged issue and got `true` again, an infinite decline/unassign/reassign loop (confirmed live: one ticket cycled 4 times before Minerva self-mitigated by marking it `blocked`, a workaround not a fix). A `not-a-seed` label now short-circuits the check.

## [0.1.0] - 2026-08-19

**Auriga's first public release: a standalone, adapter-based orchestrator with its own dashboard, showcase page, MCP server, and a real project registry — no more hardcoded, hand-edited config.**

### Added

- **Standalone adapter interface** (PRs #58, #59): the router's dispatch/state-machine core no longer talks to Multica directly — `backlogAdapter`/`spawnAdapter` interfaces sit between them, each with a real Multica-backed implementation and an in-memory stub, plus a documented, intentionally-unbuilt `pantheon-v2-l2` adapter as the only sanctioned future path into Pantheon. Auriga now runs fully standalone with zero live external systems present.
- **Operator dashboard** (PR #60): a real Vite/React read-only UI (epics list, story detail with dependency view, activity log) served by a new local HTTP API over `.pHive/` planning state — the first way to see what Auriga is doing without reading raw YAML.
- **Public GitHub Pages showcase + Star Atlas dashboard restyle** (PR #61): a public marketing/demo page at the repo's GitHub Pages site explaining what Auriga is and how to install it, plus a visual restyle of the real dashboard to match — the operator dashboard kept its tab-based navigation rather than adopting the showcase's long-scroll layout, since the two serve different audiences.
- **Operator-side MCP server + agent install/interact CLI** (PR #62): a new `auriga` command line tool — `auriga agent init`/`agent status` detects and registers Auriga's MCP server with Claude Code and Codex CLI installs, and the MCP server itself exposes three read-only tools (list board, get story detail, list blocked/in-flight) so an operator's own agent session can query Auriga's board directly, without opening the dashboard. Ships deliberately read-only in this release — write capability was scoped out pending its own safety design, not an oversight. `docs/install.sh` gives a one-line install.
- **Real, living project registry** (PR #63): `auriga project scan`/`add`/`remove`/`list` replaces the router's old hand-edited list of which Multica projects it dispatches to and which agent lane handles each one — a real operator-facing CLI instead of a source-code edit, including freeform per-project notes.
- **Core dispatch engine** (baseline, first documented in this release): capability-aware routing so hive-tagged stories always land on a Claude+plugin-hive lane; a pure state-machine covering `todo → in_review → done` transitions with auto-unblock when a dependency reaches done; a human-todo filter that routes human-owned tickets to their own queue instead of the agent dispatch pool; a repo-provisioning gate that prevents dispatch failures on unprovisioned repos; and triage passes that bulk-reassign self-blocked stories, re-evaluate stale dependency blocks, and route unplanned/mis-dispatched seeds to the Minerva planning lane.

### Fixed

- **PR-matching regression** (PR #58): the review lane's GitHub PR discovery was silently narrowing matches to raw-identifier-substring-only, dropping slug-branched PRs the router's own richer matcher would have found — the same bug class previously seen in this project (PAN-7150). Fixed by scanning the board once per cycle and filtering client-side with the full matcher.
- **`auriga_get_story` MCP tool latency** (main, post-#62): the story-detail tool's pull-request lookup did an uncached live GitHub scan across every configured repo on every call — measured at ~75 seconds against the real board. Fixed by caching the board-wide scan with a short TTL, the same fix already proven in the router's own dispatch loop — first call still pays the scan cost, every call after is ~50-60ms.
- **Dashboard security hardening** (PR #60): an unguarded `decodeURIComponent()` in the local HTTP API could crash the server, and a path-traversal gap in epic/story file resolution could read arbitrary YAML outside `.pHive/`. Both fixed with a shared path-containment guard.

### Security

- **Deep pre-publication audit** (main, pre-public): before making this repo public, a full audit of every tracked file and git history found no real secrets (API keys, tokens, credentials) anywhere. Real Multica operational identifiers (agent/project UUIDs, a workspace ID, human names) are present and have been since the router's earliest commits, but are not treated as sensitive — this repo is owned and published under the operator's own real identity.
